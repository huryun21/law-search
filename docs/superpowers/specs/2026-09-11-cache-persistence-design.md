# 클라우드 배포 캐시 영속성(R2 스냅샷 백업/복원) 설계

## 1. 문서의 지위

이 문서는 기존 스펙들(`2026-08-11-korean-law-search-design.md` 등)을 확장한다. 검색 로직, 정확 일치 우선순위, 24시간 TTL 캐시의 판정 기준(`cache.py`의 `CacheStore.get/put`)은 전혀 바꾸지 않는다. 이 문서는 "그 캐시가 담기는 SQLite 파일이 Streamlit Cloud 컨테이너 재시작 때마다 사라지는 문제" 하나만 다룬다.

## 2. 배경 — 발견된 문제

Streamlit Community Cloud 무료 티어는 다음 두 경우 컨테이너를 새로 띄운다:

1. 12시간 무방문 시 앱이 슬립되고, 다음 방문 때 재시작.
2. `main` 브랜치에 push할 때마다 자동 재배포.

두 경우 모두 로컬 디스크(`data/cache.db`)가 초기화된다. `docs/CLAUDE_HANDOFF.md`에 이미 "클라우드 SQLite 캐시는 컨테이너 재시작 시 사라지며, 이 경우 공식 API에서 다시 조회한다(정상 동작)"고 문서화돼 있으나, 실사용 결과 이게 매일 아침 첫 검색과 배포 직후 검색을 반복적으로 느리게 만드는 원인으로 확인됨.

## 3. 목표와 성공 기준

1. 컨테이너가 재시작돼도, 최소 전날 스냅샷 시점까지 캐시됐던 검색어는 계속 빠르게 응답한다.
2. 검색 자체의 속도·정확성에는 영향을 주지 않는다 — 백업/복원 로직이 실패해도 검색은 항상 정상 동작한다.
3. 로컬 개발(`run.bat`)은 지금처럼 아무 영향 없이 그대로 동작한다.
4. 별도의 예약 실행 인프라(GitHub Actions cron 등) 없이, 기존 트래픽만으로 매일 자동 백업이 이뤄진다.

## 4. 범위

### 포함

- Cloudflare R2에 `cache.db` 전체 파일을 스냅샷으로 저장/복원.
- 컨테이너 시작 시(로컬 파일이 없을 때) R2에서 최신 스냅샷을 내려받아 복원.
- 매일 오후 5시(KST) 이후 첫 요청 처리 시, 그날 아직 백업 안 했으면 현재 `cache.db`를 R2로 업로드.
- R2 자격증명을 `st.secrets`/`config.local.toml` 패턴으로 관리(기존 `LAW_API_KEY` 처리 방식과 동일).

### 제외

- 방문자가 전혀 없는 날의 "무조건 5시 실행" 보장 — 이번 범위에서는 트래픽 기반(기회적) 트리거만 구현한다. 필요해지면 별도로 헤드리스 브라우저 예약 방문을 추가한다(§9 참고).
- 증분/부분 백업 — 파일 전체를 매번 통째로 덮어쓴다. 캐시 파일 크기가 문제가 될 만큼 커지면 그때 재검토한다.
- 캐시 자체의 TTL·키 구조 변경 — `CacheStore`의 기존 로직은 그대로다.
- 서울시 정비사업 자료(cleanup.seoul.go.kr) 검색 기능 — 별개 스펙으로 다룬다.

## 5. 아키텍처

### 5.1 저장 위치

Cloudflare R2(S3 호환) 버킷에 고정된 키 하나(`cache-snapshot.db`)로 저장한다. 버전 관리 없이 매번 덮어쓴다 — 필요한 건 "가장 최근 스냅샷" 하나뿐이다. `boto3`로 접근한다(S3 호환 API 표준 클라이언트).

### 5.2 새 모듈 — `src/lawsearch/cache_backup.py`

이 모듈은 `CacheStore`나 검색 로직을 전혀 모른다 — 순수하게 "로컬 파일 경로 ↔ R2의 고정 키" 사이의 업로드/다운로드만 담당한다.

- `restore_if_missing(cache_path: Path, r2_config: R2Config | None) -> None`
  로컬에 `cache_path` 파일이 이미 있으면 아무것도 안 한다. 없고 `r2_config`도 있으면 R2에서 내려받아 그 경로에 저장한다. R2에 객체가 아직 없거나(첫 배포) 접속 실패하면 조용히 넘어간다 — 로컬 파일이 없는 채로 진행되면 `CacheStore`가 새 빈 DB를 만드는 지금과 동일한 동작이 된다.

- `maybe_backup(cache_path: Path, r2_config: R2Config | None, *, now: Callable[[], datetime] = ...) -> None`
  `r2_config`가 없으면(로컬 개발) 아무것도 안 한다. 있으면: 현재 시각(Asia/Seoul)이 17시 이후이고, 이 프로세스가 오늘 날짜로 아직 백업한 적 없으면 업로드하고 "오늘 날짜"를 프로세스 메모리 안 전역 변수에 기록한다. 이미 오늘 백업했으면 아무것도 안 한다.

  "오늘 백업했는지"를 DB나 파일에 영속시키지 않고 **프로세스 메모리에만** 둔다 — 컨테이너가 재시작되면 이 플래그도 같이 리셋되지만, 그래봐야 재시작 후 첫 방문 때 한 번 더(중복) 업로드하는 정도라 무해하다. 별도의 영속 저장소를 또 만드는 것보다 훨씬 단순하다.

### 5.3 호출 지점 — `app.py`

- `_load_resources()`(현재 `st.cache_resource`로 컨테이너 수명 동안 한 번만 실행됨)에서 `Settings`를 만든 직후 `restore_if_missing()`을 호출한다 — 이 함수가 캐시된 리소스이므로, 복원은 컨테이너당 정확히 한 번만 일어난다.
- `main()` 맨 앞(모든 요청마다 실행됨)에서 `maybe_backup()`을 호출한다 — 매 요청마다 값싼 시간 비교만 하고, 조건이 맞을 때만 실제 업로드가 일어난다.

### 5.4 로컬 개발과의 분기

`r2_config`는 `config.py`의 `load_settings()`가 `st.secrets`(클라우드) 또는 환경변수에서 R2 관련 값 3종(계정ID·액세스키·버킷명)을 찾았을 때만 채워진다. 로컬 `config.local.toml`에는 이 값이 없으므로 `r2_config`가 항상 `None`이고, 위 두 함수는 즉시 반환한다 — 로컬 동작은 지금과 완전히 동일하다.

## 6. 오류와 경계 상황

- R2 접속 실패(네트워크, 자격증명 오류, 버킷 없음 등)는 어떤 경우에도 검색 흐름을 막거나 화면에 에러로 노출하지 않는다 — 로그 경고만 남기고 넘어간다(기존 `_logger.warning` 패턴).
- R2 자격증명 값 자체는 로그·에러 메시지·화면에 절대 노출하지 않는다(`CLAUDE.md`의 기존 원칙을 이 새 자격증명에도 동일하게 적용).
- 백업 업로드 도중 앱이 재시작돼도(드묾) 이전 스냅샷이 그대로 R2에 남아있으므로 데이터가 깨지지 않는다 — 실패한 업로드는 단순히 반영이 안 될 뿐이다.

## 7. 테스트 전략

- `restore_if_missing`/`maybe_backup`은 R2 클라이언트를 얇은 인터페이스로 감싸 페이크(가짜) 구현으로 단위 테스트한다(기존 `FakeApi`/`httpx.MockTransport` 패턴과 동일한 철학) — 실제 R2에 접속하는 테스트는 만들지 않는다.
- 케이스: 로컬 파일 있음(복원 스킵) / 로컬 파일 없음+R2에 있음(복원됨) / 로컬 파일 없음+R2도 없음(조용히 스킵) / R2 접속 예외(조용히 스킵, 검색 흐름 안 막힘).
- `maybe_backup`: 17시 이전(스킵) / 17시 이후+오늘 첫 호출(업로드) / 17시 이후+오늘 이미 업로드함(스킵) / `r2_config` 없음(항상 스킵).
- 전체 `pytest -q` 통과, 기존 캐시/검색 테스트는 이번 변경으로 회귀가 없어야 한다.

## 8. 구현 순서

1. `cache_backup.py` 모듈 + 단위 테스트(§7) — R2 없이도 완전히 검증 가능.
2. `config.py`에 R2 설정 3종 로딩 추가(`load_settings`/`resolve_api_key`와 같은 패턴).
3. `app.py`의 `_load_resources`/`main()`에 호출 지점 연결.
4. 로컬에서 `r2_config=None`일 때 기존 동작과 동일한지 회귀 테스트로 고정.
5. 실제 R2 버킷 생성 + `.streamlit/secrets.toml`(사용자가 대시보드에서 직접 입력, Git에 넣지 않음) 값 채우기 — 배포 후 하루 이상 관찰하며 실제 백업/복원이 도는지 확인.

## 9. 나중에 고려할 것 (이번 범위 밖)

방문자가 전혀 없는 날에도 반드시 백업이 돌아야 한다면, GitHub Actions cron + 헤드리스 브라우저(Playwright)로 오후 5시에 실제 방문을 일으키는 방식을 추가로 검토한다(§4 제외 참고) — 다만 이는 앱을 슬립에서 깨우는 부수효과도 있으므로, 그 시점에 "슬립 방지"까지 같이 할지 사용자와 다시 상의한다.
