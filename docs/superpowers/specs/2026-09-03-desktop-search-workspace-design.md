# 법령 통합검색 데스크톱 워크스페이스 및 팀 공유 설계

## 1. 문서의 지위

이 문서는 `2026-08-11-korean-law-search-design.md`를 확장한다. 기존 검색 문법, 정확도 기준, 지역 우선순위, 공식 API 검증, SQLite 캐시 및 보안 원칙은 유지한다. 이 문서는 다음 영역에서 기존 설계를 대체한다.

- 데스크톱 기본 화면과 결과 탐색 방식
- 본문 미리보기와 두 문서 비교 방식
- 로컬 전용 실행에서 소규모 팀용 비공개 배포로의 확장

AI 요약과 법률적 판단은 계속 제외한다.

## 2. 목표와 성공 기준

사용자는 한 번의 검색으로 관련 법률, 대통령령, 총리령·부령, 행정규칙, 광역 및 기초 자치법규를 모두 확인한다. 기본 화면에서는 전체 결과를 빠르게 훑고, 필요한 문서만 본문 미리보기로 연다. 필요할 때에는 법규 종류와 관계없이 두 문서를 좌우로 비교한다.

성공 기준은 다음과 같다.

1. 검색 결과가 데스크톱 화면의 제한된 폭 안에서 2열 카드로 촘촘히 표시된다.
2. 사이드바는 결과를 숨기는 필터가 아니라 법규 유형별 바로가기와 건수 표시로 동작한다.
3. 사이드바 이동과 이미 열린 미리보기의 재열람은 공식 API를 다시 호출하지 않는다.
4. 상세 본문이 필요한 경우에만 지연 로딩하며, 한 번 불러온 본문은 세션과 SQLite 캐시에서 재사용한다.
5. 비교 화면의 좌우에는 현재 검색 결과의 어떤 자료 유형이든 독립적으로 선택할 수 있다.
6. 본문을 불러오지 못해도 공식 원문 링크와 검색 결과 메타데이터는 유지된다.
7. 약 10명의 내부 사용자가 개인 PC가 꺼진 상태에서도 비공개 URL로 접속할 수 있다.
8. API 인증값은 Git, SQLite, 로그, 오류 메시지와 화면에 남지 않는다.

## 3. 범위

### 포함

- 데스크톱 우선 반응형 레이아웃
- 법규 유형별 사이드바 바로가기
- 법규 유형별 2열 요약 카드
- 단일 문서 본문 미리보기
- 임의의 두 검색 결과를 좌우로 비교
- 본문 지연 로딩 및 기존 24시간 SQLite 캐시 재사용
- Streamlit Community Cloud 비공개 배포 준비
- 로컬 파일 기반 인증과 클라우드 비밀값 기반 인증의 병행 지원
- 배포 및 Claude Code 인수인계 문서

### 제외

- AI 요약, 의미 기반 차이 분석, 법적 결론 생성
- 법률과 하위 규정의 위임 관계 자동 확정
- 서로 다른 조문의 자동 의미 정렬
- 현재 검색결과 밖의 문서를 비교 화면 안에서 별도로 재검색
- 사용자별 검색 기록과 즐겨찾기
- 모바일 전용 UX 최적화
- Azure 이전 자동화

화면은 좁은 폭에서도 한 열로 재배치되지만, 이번 구현과 인수 테스트의 우선 대상은 데스크톱이다.

## 4. 화면 구조

### 4.1 공통 상단

상단은 최대 콘텐츠 폭 안에 다음 요소만 둔다.

- 서비스명
- 검색 예시
- 출처 및 법적 고지의 축약 표시
- 검색창과 검색 버튼
- 선택 지역 표시와 해제 버튼
- 공식 API 새로고침
- `기본 보기`와 `비교하기` 전환

현재처럼 출처와 경고가 브라우저 전체 폭을 차지하지 않게 한다. 검색 폼은 Enter 제출을 유지한다.

### 4.2 사이드바

사이드바는 검색이 완료된 뒤 표시하며 다음 트리를 사용한다.

```text
상위법령
  법률
  대통령령(시행령)
  총리령·부령(시행규칙)
  행정규칙
  기타 법령
자치법규
  선택 광역지자체 조례·규칙
  선택 기초지자체 조례·규칙
```

각 항목에는 현재 검색결과 건수를 표시한다. 항목을 펼치면 해당 그룹의 법령명을 볼 수 있다. 그룹명 또는 법령명을 누르면 이미 렌더링된 본문 위치로 이동하거나 해당 문서를 미리보기로 선택한다. 이 동작은 검색 또는 본문 API를 호출하지 않는다.

사이드바 선택으로 다른 결과를 자동으로 숨기지 않는다. 전체 결과는 기본 화면에 계속 남는다.

### 4.3 기본 보기: 2열 요약 카드

검색 결과는 기존 관련도 및 지역 우선순위를 보존한 상태로 그룹별로 표시한다. 각 그룹 안에서는 데스크톱 기준 2열, 좁은 화면에서는 1열로 배치한다.

카드는 다음 정보만 표시한다.

- 법령명
- 법규 종류
- 소관기관 또는 지자체
- 현행·연혁 여부
- 공포일과 시행일
- 제목 일치 또는 본문 일치 표시
- 검색 중 검증된 정확 일치 조문 한 줄
- `미리보기`와 `공식 원문` 동작

제목은 최대 두 줄, 일치 조문은 최대 두 줄까지만 카드에서 보인다. 상세 내용은 카드 높이를 늘리지 않고 미리보기에서 확인한다. `비교` 버튼을 카드마다 반복하지 않고 공통 상단에 `비교하기` 버튼 하나를 둔다.

### 4.4 단일 문서 미리보기

카드나 사이드바 법령명을 선택하면 사이드바는 유지하고 카드 영역을 단일 문서 미리보기로 전환한다.

미리보기는 다음 순서로 표시한다.

1. 법령명, 종류, 소관기관, 시행일
2. 공식 원문 링크
3. 검색어와 정확히 일치하는 조문 수
4. `제○조`, `제○항`, `제○호`, `○목` 위치
5. 일치 구절과 필요한 앞뒤 문맥
6. 일치 조문이 여러 개인 경우 조문 선택

`검색결과로 돌아가기`는 세션에 저장된 검색 결과를 다시 보여주며 API를 호출하지 않는다. 본문 조회가 실패하면 “본문을 불러오지 못했습니다”라는 상태와 공식 원문 링크를 함께 표시한다. 정확 일치 조문이 없으면 무관한 메타데이터를 대신 보여주지 않는다.

### 4.5 비교 보기

`비교하기`를 누르면 사이드바를 유지한 채 주 콘텐츠 영역만 좌우 두 칸으로 나눈다.

각 칸은 독립적으로 다음을 제공한다.

- 현재 검색결과의 문서 선택
- 선택 문서의 메타데이터
- 정확 일치 조문 선택
- 조문 본문 미리보기
- 공식 원문 링크

비교 대상은 법률과 조례로 제한하지 않는다. 법률 대 법률, 시행령 대 시행규칙, 시행규칙 대 조례 등 모든 조합을 허용한다.

비교 화면은 두 문서의 조문을 나란히 표시할 뿐 법적 위임 관계, 우선순위 또는 내용 차이를 자동 판정하지 않는다. 화면에는 “키워드 일치 조문을 나란히 표시하며 법적 연계 관계를 자동 확정하지 않습니다”라는 안내를 표시한다.

초기 버전의 선택 목록은 현재 검색결과로 한정한다. 비교 화면 안의 독립 검색은 동일 기능을 중복시키므로 제외한다.

## 5. 데이터 모델과 상태

### 5.1 검색 결과의 미리보기 문맥

`SearchResult`에 선택적 `match_context`를 추가한다. 본문 검색 결과를 검증할 때 `DetailResponse.contexts`의 첫 번째 정확 일치 문맥을 저장한다. 제목만 정확히 일치하여 본문 검증을 생략한 결과는 `match_context=None`을 유지한다.

이 값은 다음 목적으로만 사용한다.

- 카드의 일치 조문 한 줄
- 이미 검증한 본문을 다시 호출하지 않기 위한 표시 정보

전체 본문과 모든 일치 조문은 기존 상세 본문 캐시에만 저장한다.

### 5.2 UI 세션 상태

Streamlit 세션 상태에는 다음 식별자만 저장한다.

- `view_mode`: `results`, `preview`, `compare`
- `selected_result_key`
- `compare_left_result_key`
- `compare_right_result_key`
- 좌우에서 선택한 조문 인덱스
- 검색 결과와 상세 조회 응답

결과 식별자는 `source + uid` 조합을 사용한다. API 인증값은 세션 상태에 저장하지 않는다.

새 검색을 실행하면 미리보기 및 비교 선택 상태를 초기화한다. 공식 API 새로고침은 검색 결과와 현재 키워드에 종속된 상세 상태를 무효화한다.

## 6. 로딩과 캐시 정책

### 6.1 검색

기존과 같이 자료원별 검색을 병렬 실행하고 결과를 세션에 저장한다. 사이드바와 카드 렌더링은 저장된 결과만 사용한다.

### 6.2 본문

- 본문 검색 결과는 검색 정확도 검증 과정에서 이미 상세 API를 호출하므로 그 결과를 SQLite에 저장하고 카드 문맥으로 재사용한다.
- 제목 일치 결과는 사용자가 처음 미리보기를 열 때 상세 API를 호출한다.
- 한 번 연 상세는 Streamlit 세션과 24시간 SQLite 캐시에서 재사용한다.
- 모든 제목 일치 결과를 검색 직후 미리 가져오지 않는다. 초기 검색시간과 API 호출량을 불필요하게 늘리기 때문이다.
- 비교 화면에서 캐시에 없는 두 문서가 동시에 필요하면 하나의 API 클라이언트 안에서 제한된 동시성으로 가져온다.

클라우드의 SQLite는 단기 성능 최적화일 뿐 영구 저장소가 아니다. 앱 재시작으로 캐시가 사라져도 공식 API에서 다시 조회하면 기능이 정상 동작해야 한다.

## 7. 구성요소 경계

### `lawsearch.app`

검색, 결과, 미리보기, 비교 모드의 상태 전환과 Streamlit 렌더링을 조정한다. API 응답 구조나 일치도 계산을 직접 처리하지 않는다.

### `lawsearch.viewmodels`

새 모듈로 둔다. 검색 결과를 사이드바 그룹, 카드 행, 문서 선택 목록으로 변환하는 순수 함수를 제공한다. Streamlit에 의존하지 않는다.

### `lawsearch.service`

검색 및 상세 조회, 본문 검증, 캐시 재사용을 담당한다. 검증 중 확보한 첫 문맥을 `SearchResult.match_context`에 전달한다. 비교용 두 상세 조회도 이 계층을 통해 수행한다.

### `lawsearch.detail`

법령 응답에서 조·항·호·목 위치와 정확 일치 문맥을 추출한다. AI나 유사 의미 추론을 사용하지 않는다.

### `lawsearch.config`

로컬 키 파일과 클라우드 비밀값 중 사용 가능한 인증 소스를 선택한다. `Settings`에는 인증값 자체를 저장하지 않는다.

## 8. 비공개 팀 배포

### 8.1 배포 대상

초기 팀 공유는 Streamlit Community Cloud의 비공개 앱으로 한다. GitHub 저장소를 배포 원본으로 사용하고, 약 10명의 팀원을 이메일 뷰어로 초대한다. 사용량은 인당 하루 1~2회 수준을 가정한다.

Community Cloud의 공식 안내에 따르면 비공개 앱은 이메일로 뷰어를 초대할 수 있으며, 현재 워크스페이스당 비공개 앱은 한 개로 제한된다. 이 제한이 문제가 되거나 조직 보안 요구가 높아지면 같은 애플리케이션 계층을 Azure로 이전한다.

### 8.2 저장소 준비

- 루트에 Community Cloud용 `streamlit_app.py` 진입점을 둔다.
- 배포 환경이 프로젝트 패키지를 설치할 수 있도록 `requirements.txt`를 추가하고 테스트한 Streamlit 버전을 고정한다.
- `.streamlit/secrets.toml`, `config.local.toml`, SQLite, 로그와 `.superpowers/`를 Git에서 제외한다.
- README에 로컬 실행과 Community Cloud 배포 절차를 분리해 기록한다.

### 8.3 인증정보

로컬은 기존 `LAW_API_KEY_FILE` 또는 `config.local.toml`의 외부 키 파일을 사용한다. Community Cloud는 앱의 Advanced settings에 다음 비밀값을 저장한다.

```toml
LAW_API_KEY = "승인받은 키"
```

앱은 `st.secrets`에서 값을 읽어 API 클라이언트를 만들 때만 전달한다. 저장소, 설정 객체, SQLite, 로그와 사용자 화면에는 기록하지 않는다. 로컬 `.streamlit/secrets.toml`도 Git에 포함하지 않는다.

### 8.4 배포 갱신

`main` 브랜치에 반영된 코드가 배포 원본이다. GitHub 변경은 Community Cloud에서 자동 반영된다. 의존성 변경은 재설치를 유발할 수 있으므로 정확한 버전을 고정한다.

## 9. 오류와 경계 상황

- 검색 자료원 하나가 실패해도 성공한 그룹은 카드로 표시한다.
- 상세 본문 실패는 해당 미리보기 또는 비교 칸에만 영향을 준다.
- 비교 한쪽이 실패해도 반대쪽 본문은 유지한다.
- 공식 링크가 허용된 `law.go.kr` HTTPS 주소가 아니면 버튼을 만들지 않는다.
- 검색결과가 한 건뿐이면 비교 화면은 같은 문서를 양쪽에 중복 선택하지 않고 두 번째 문서가 필요하다고 안내한다.
- 검색결과가 없으면 빈 사이드바와 빈 카드틀을 만들지 않는다.
- 연혁 자료는 현행 자료보다 뒤에 두고 명확히 표시한다.
- 제목 일치 결과의 미리보기를 열었으나 본문에 키워드가 없으면 “정확히 일치하는 조문 없음”으로 표시하고 임의의 조문을 보여주지 않는다.

## 10. 테스트 전략

### 단위 테스트

- 사이드바 그룹과 카드 그룹이 기존 우선순위를 보존한다.
- 각 카드 행에 최대 두 결과만 배치된다.
- 본문 검증 결과의 첫 문맥이 `match_context`로 전달된다.
- 제목 일치 결과는 상세 API를 미리 호출하지 않는다.
- 새 검색과 강제 새로고침이 UI 선택 상태를 올바르게 초기화한다.
- 모든 `SourceGroup` 조합을 좌우 비교 대상으로 선택할 수 있다.
- 비교 선택 목록이 현재 검색결과만 포함한다.
- 잘못된 공식 URL이 버튼으로 렌더링되지 않는다.
- `Settings`와 직렬화 가능한 상태에 API 인증값이 없다.
- 로컬 키 파일과 Streamlit 비밀값 경로가 각각 동작한다.

### 통합 테스트

- 본문 검증으로 채워진 캐시가 카드 미리보기에서 추가 API 호출 없이 사용된다.
- 제목 일치 결과는 첫 미리보기에서 한 번만 API를 호출하고 이후 캐시를 사용한다.
- 비교 양쪽의 캐시 적중과 부분 실패를 독립적으로 처리한다.
- 검색 후 사이드바 이동과 결과 화면 복귀가 API 호출 수를 늘리지 않는다.

### 수동 인수 테스트

1. 데스크톱에서 `방화구획`을 검색하면 그룹별 2열 카드가 표시된다.
2. 사이드바에서 시행령을 누르면 시행령 카드 구역으로 즉시 이동한다.
3. 미리보기를 열고 결과로 돌아와도 검색 API를 재호출하지 않는다.
4. 같은 문서 미리보기를 다시 열면 지연 없이 표시된다.
5. 비교 화면에서 `건축법 시행령`과 관련 부령을 좌우에 선택할 수 있다.
6. 비교 화면에서 법률 대 법률 및 조례 대 시행규칙 조합도 선택할 수 있다.
7. 일치 조문이 없는 자료는 임의 문맥을 표시하지 않는다.
8. 비공개 배포 URL에 초대된 팀원만 접근할 수 있다.
9. 저장소, 로그와 캐시에서 API 인증값이 발견되지 않는다.
