# 검색 결과 입법예고·행정예고 연계 설계

## 1. 문서의 지위

이 문서는 `2026-08-11-korean-law-search-design.md`와 `2026-09-03-desktop-search-workspace-design.md`를 확장한다. 기존 검색 문법, 정확도 기준, 캐시·보안 원칙은 그대로 유지한다. 이 문서는 검색 결과에 진행 중인 입법예고·행정예고가 있는지 함께 보여주는 새 기능 하나만 다룬다.

AI 요약과 법률적 판단은 계속 제외한다. 이 기능도 마찬가지로 예고 여부를 참고로 보여줄 뿐, 예고 내용에 대한 해석이나 전망을 만들어내지 않는다.

## 2. 목표와 성공 기준

사용자가 법령을 검색했을 때, 그 법령에 진행 중인 입법예고(법률·대통령령 개정안) 또는 행정예고(행정규칙 제정·개정안)가 있으면 놓치지 않고 알 수 있다.

성공 기준:

1. 검색 결과 카드 중 입법예고·행정예고가 진행 중인 법령에는 배지가 붙는다.
2. 매칭된 게 하나라도 있으면 검색창 바로 아래에 요약 줄이 뜬다. 없으면 그 줄 자체가 없다.
3. 매칭은 법령명 **정확 일치**만 인정한다. 부분일치·유사어 확장은 하지 않는다 — 기존 본문 검색의 "정확 일치" 원칙을 그대로 적용한다.
4. 검색 속도에 미치는 영향은 거의 없다 — 예고 목록은 검색 결과별로 조회하지 않고, 별도로 캐시된 전체 목록에서 로컬로만 대조한다.
5. 이 기능에 필요한 설정(별도 API 인증값)이 없으면 화면에는 아무 흔적도 남지 않는다 — 로딩 표시, 빈 칸, 에러 메시지 전부 없다.
6. 이 기능 호출이 실패해도 검색 결과 자체(법령·행정규칙·자치법규)는 정상적으로 표시된다.

## 3. 범위

### 포함

- 법제처 국민참여입법센터(`opinion.lawmaking.go.kr`)의 입법예고·행정예고 목록 조회 API 연동
- 진행 중(예고 종료 안 됨)인 예고만 조회
- 검색 결과의 법령명·행정규칙명과 예고 목록의 관련법령명을 정확 일치로 대조
- 대조 결과를 카드 배지 + 검색창 아래 요약 줄로 표시
- 예고 목록 전체를 기존 SQLite 캐시와 같은 방식으로 24시간 캐시
- 설정이 없을 때(현재의 Streamlit Cloud 배포) 기능 전체를 조용히 비활성화

### 제외

- moleg.go.kr 페이지 스크래핑 (공식 API로 대체됨)
- 예고 내용 요약·해석·의견 제출 대행
- Streamlit Cloud에서의 즉시 활성화 — IP 화이트리스트 문제가 해결(등록 IP 안정화 또는 재승인 절차 확립)된 뒤 별도로 판단
- 백그라운드 상시 모니터링(스케줄러, 알림 발송) — 검색 시점 확인으로 충분하다고 판단됨

## 4. 데이터 소스와 인증

- 엔드포인트: `https://www.lawmaking.go.kr/rest/ptcpAdmPp.{xml|json}` (행정예고) 및 대응하는 입법예고용 엔드포인트(정확한 경로는 API 가이드에서 승인 후 재확인).
- 인증: `OC` 쿼리 파라미터. 값은 `opinion.lawmaking.go.kr` 가입 계정 ID의 `@` 앞부분. law.go.kr의 기존 OC 키와는 **별개의 값**이며 별도로 관리한다.
- 이 API는 **IP 화이트리스트** 방식이다. 신청 시 등록한 서버 IP에서만 호출이 허용된다. 현재는 사용자 로컬 PC의 공인 IP만 등록되어 있으므로, 이 기능은 로컬 실행에서만 동작한다.
- 인증값은 기존 원칙을 그대로 따른다 — 소스·Git·로그·화면에 노출하지 않는다. `config.local.toml`에 `lawmaking_oc_file` 같은 새 키로 로컬 키 파일 경로만 추가한다. **Streamlit Cloud의 `st.secrets`에는 의도적으로 이 값을 넣지 않는다** — 이것이 클라우드에서 기능을 끄는 유일한 스위치다.

## 5. 아키텍처와 구성요소 경계

새 모듈 `src/lawsearch/notices.py` 하나로 완결시킨다. 기존 `SearchResult`/`SearchResponse`/`SearchService`는 수정하지 않는다.

- `NoticeApiClient` — `LawApiClient`와 별도 클래스. 별도 도메인·별도 인증 파라미터(OC 위치·IP 제한 방식이 다름)를 하나의 클래스에 억지로 합치지 않는다.
- `fetch_active_notices(settings) -> tuple[Notice, ...]` — 진행 중인 예고 전체를 가져와 24시간 SQLite 캐시(기존 `CacheStore`와 같은 테이블 구조 또는 새 테이블)에 저장. 캐시가 유효하면 API를 다시 부르지 않는다.
- `match_notices(results, notices) -> Mapping[str, Notice]` — 순수 함수. `SearchResult.title`과 `Notice`의 관련법령명이 정규화 후 정확히 같을 때만 매칭. 부작용 없음, 단위 테스트로 독립 검증 가능.
- `app.py`는 검색 결과를 얻은 뒤, `lawmaking_oc_file`(또는 대응 설정)이 있을 때만 `fetch_active_notices` + `match_notices`를 호출해 매칭 결과를 세션 상태에 얹는다. 설정이 없으면 이 경로 자체를 타지 않는다.

## 6. 매칭 로직

- 대조 기준 문자열: 검색 결과의 공식 법령명/행정규칙명 전체 문자열과, 예고 목록 응답의 관련법령명(정확한 필드명은 §9 참고)을 각각 공백 정규화 후 완전 일치 비교.
- 하나의 예고가 여러 관련법령을 가질 수 있으면(콤마 구분 등), 그 목록 안에 검색 결과 제목과 완전히 같은 항목이 있을 때만 매칭.
- 매칭에 실패해도(즉, 예고 쪽에 이 법령이 없어도) 검색 결과 표시에는 아무 영향이 없다 — 배지가 안 붙을 뿐이다.

## 7. 캐시와 새로고침 정책

- 예고 전체 목록은 검색어와 무관하게 **하나의 캐시 항목**으로 저장한다(기존처럼 검색어별 캐시가 아니다).
- TTL은 기존 법령 검색과 동일하게 24시간.
- 캐시가 오래된 뒤 **처음 검색하는 요청**이 새로고침 비용을 부담한다(기존 캐시와 동일한 동작, 새로운 트레이드오프 아님).
- 캐시 갱신이 실패하면(API 에러) 오래된 캐시가 있으면 그걸 계속 쓰고, 없으면 이번 검색에서는 예고 정보 없이 진행한다.

## 8. 화면 표시

- **카드 배지**: 매칭된 결과 카드 제목 옆에 `🔔 입법예고 중` 또는 `🔔 행정예고 중` 태그. 기존 "연관 검색어" 칩과 같은 시각 언어(작은 pill 형태)를 재사용한다.
- **요약 줄**: 검색창 바로 아래, 검색 결과 렌더링 전에 `⚠️ 이번 검색 결과 중 N건에 입법예고·행정예고가 진행 중입니다.` 형태로 노출. 매칭 0건이면 이 줄 자체를 렌더링하지 않는다.
- 배지나 요약 줄 클릭 시 소관부처·예고기간·공식 페이지 링크 등 상세 정보를 보여준다(정확한 항목·레이아웃은 실제 API 응답 필드 확인 후 확정).

## 9. 클라우드/로컬 조건부 노출

- 판단 기준은 "클라우드냐 로컬이냐"가 아니라 **"설정값이 있느냐 없느냐"**다. `config.py`의 기존 설계 철학(설정 없음 = 에러 아님, 그냥 그 경로를 안 씀)을 그대로 재사용한다.
- 지금은 로컬에만 IP가 등록돼 있어 사실상 로컬 전용이지만, 코드는 "로컬/클라우드"를 구분하지 않는다 — 나중에 클라우드 IP까지 등록되고 `st.secrets`에 값을 추가하면 코드 변경 없이 팀원들에게도 열린다.

## 10. 오류와 경계 상황

- API 인증 실패(403 등, 예: 등록 안 된 IP에서 호출) — 예고 정보 없이 검색 결과만 표시. 에러를 화면에 보여주지 않는다(§2의 성공 기준 6).
- API 응답 형식이 예상과 다름(행정규칙 상세조회에서 이미 한 번 겪은 문제) — 방어적으로 파싱하고, 실패하면 해당 항목만 건너뛴다.
- 예고 목록이 비어 있음(현재 진행 중인 예고가 하나도 없음) — 정상 상태. 요약 줄 없이 검색 결과만 표시.

## 11. 테스트 전략

- `match_notices()`는 순수 함수이므로 다양한 입력(정확 일치, 부분일치만 되는 경우, 여러 관련법령 중 하나만 일치, 예고 없음)에 대한 단위 테스트를 API 접근 없이 작성한다.
- `NoticeApiClient`는 기존 `LawApiClient` 테스트처럼 `httpx.MockTransport`로 요청 형식을 검증한다(인증값이 URL에 노출되지 않는지 포함).
- 설정이 없을 때 `app.py`가 이 기능 경로를 아예 타지 않는지 확인하는 회귀 테스트를 추가한다(화면에 관련 텍스트가 전혀 없음을 단언).
- 실제 API 승인 후, 캡처한 실응답으로 `match_notices()`가 실제 법령명과 올바르게 맞물리는지 한 번 더 확인한다.

## 12. 남은 미확정 사항 (API 승인 후 확정)

- 입법예고 목록 조회의 정확한 엔드포인트 경로와 응답 필드명(행정예고의 `ptcpAdmPp`에 대응하는 입법예고 쪽 이름).
- 응답의 관련법령명 필드가 실제로 어떤 이름인지, 콤마 구분 다중 값인지 여부.
- 캐시 저장에 기존 `CacheStore`를 재사용할지, 별도 테이블을 둘지(예고 목록은 검색어 기반이 아니므로 키 구조가 다름).
- 상세 정보 표시 레이아웃의 정확한 항목 구성.

## 13. 구현 순서

1. `NoticeApiClient` — httpx 기반, 요청 파라미터·인증값 비노출 테스트 먼저.
2. `Notice` 데이터 모델 + 응답 파싱(실제 API 승인 후 진행).
3. `match_notices()` 순수 함수 + 단위 테스트.
4. 캐시 계층(전체 목록 24시간 캐시).
5. `app.py` 연동 — 설정 없을 때 조용히 비활성화되는지 회귀 테스트부터.
6. 카드 배지 + 요약 줄 렌더링.
7. 로컬 수동 검증(실제 진행 중인 예고로 배지가 뜨는지).
