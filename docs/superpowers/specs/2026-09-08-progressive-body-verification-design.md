# 본문 검증 전체 회수율 확보와 단계적(점진적) 결과 표시 설계

## 1. 문서의 지위

이 문서는 `2026-08-11-korean-law-search-design.md`와 `2026-09-03-desktop-search-workspace-design.md`를 확장한다. 기존 화면 구조(사이드바 트리, 법률/대통령령/총리령·부령/행정규칙/자치법규 그룹, 카드·미리보기·비교), 정확 일치 우선순위, 캐시·보안 원칙은 그대로 유지한다. 이 문서는 "본문 검색 후보가 매우 많을 때(수백 건 이상) 일부만 확인하고 나머지를 놓치는 문제"와 "그걸 고치면서도 체감 속도를 지키는 방법" 하나만 다룬다.

## 2. 배경 — 발견된 문제

"통합심의" 검색에서 법률 본문 후보가 806건이었는데, 코드가 1페이지(100건)만 가져왔다. 법제처 API는 관련도순이 아니라 **법령명 가나다순**으로 결과를 주기 때문에, "도시 및 주거환경정비법"(과 그 시행령)처럼 이름이 뒤쪽 순번에 오는 문서는 실제로 검색어가 본문에 있어도 후보 목록에 들어오지 못해 검증 자체가 안 되고 조용히 빠졌다.

이 문제는 `CLAUDE.md`가 이미 규정한 "본문 정확 일치가 없으면 표시하지 않는다"는 원칙과는 다른 층위의 정확성 문제다 — 이번 문제는 문구 오탐(false positive)이 아니라 **문서 자체가 후보에도 못 들어가서 생기는 누락(false negative, 회수율 문제)**이다. 두 문제 모두 이 앱의 핵심 가치(정확성)에 해당하므로 회수율 쪽도 고쳐야 한다.

## 3. 목표와 성공 기준

1. 본문 검색 후보가 아무리 많아도(API가 주는 `totalCnt` 전체) 페이지 상한 때문에 후보 자체가 빠지는 일이 없다.
2. 그러면서도 사용자가 체감하는 첫 결과 표시 속도는 지금과 비슷하거나 낫다.
3. 화면 전체가 깜빡이거나 스크롤 위치가 튀는 진행 방식은 쓰지 않는다.
4. 나중에 더 확인된 결과는 사용자가 버튼을 누르지 않아도 자동으로 해당 그룹(법률/대통령령/총리령·부령/행정규칙/자치법규)에 반영된다.
5. 기존 화면 구조(그룹·카드·사이드바·미리보기·비교)는 바뀌지 않는다 — "언제 채워지는가"만 달라진다.

## 4. 범위

### 포함

- `lawSearch.do` 계열 호출에서 `totalCnt`까지 모든 페이지를 가져오도록 변경(현재는 1페이지 고정).
- 가져온 본문 후보를 "우선순위"와 "나머지"로 나누는 순수 분류 로직.
- 우선순위 후보만 먼저 본문 검증 후 즉시 렌더링.
- 나머지 후보를 `st.fragment(run_every=...)`로 점진적으로 검증하며, 진행 상태를 그 조각(fragment)만 다시 그려서 표시.
- 검증이 끝난 나머지 후보는 자동으로 기존 그룹에 추가.

### 제외

- 우선순위 키워드 목록의 확정 값 — 사용자가 추후 제공(§9).
- 실제 백그라운드 스레드/프로세스 — Streamlit의 세션당 단일 스크립트 실행 모델을 유지하며, fragment의 주기적 재실행으로 점진적 진행을 흉내낸다.
- 브라우저 알림/이메일 등 외부 알림 — 완료 표시는 화면 안 상태 텍스트로 충분하다(사용자 확인됨).
- 검색어 자체의 정확 일치 판정 로직 변경 — `detail.py`의 정확 일치 기준은 그대로다. 이 설계는 "검증 대상에 오르는가"만 다룬다.

## 5. 아키텍처

### 5.1 후보 수집 — 전체 페이지 조회

`SearchService`가 각 자료원(`laws`, `admin_rules`, `municipal`, `provincial`)을 조회할 때, 1페이지 응답의 `totalCnt`를 보고 남은 페이지를 전부 순차 또는 제한된 동시성으로 마저 가져온다. 페이지 상한을 두지 않는다 — 진행 상태를 점진적으로 보여주는 방식으로 바뀌므로, "몇 페이지까지 볼까"라는 트레이드오프 자체가 없어진다.

**2026-09-09 결정 기록 (최종 브랜치 리뷰):** 상한을 두지 않는 이 설계는 이론상 비정상적으로 큰 `totalCnt`나 `page`를 무시하는 API 응답에 대해 요청 수를 무한정 늘릴 수 있다는 지적이 있었다. 신뢰된 정부 API를 대상으로 하는 소규모 내부 도구라는 점, 그리고 이 기능 전체가 "실제로 존재하는 일치 문서를 페이지 상한 때문에 놓치는 일이 없어야 한다"는 요구에서 시작됐다는 점을 근거로, 상한 없음을 그대로 유지하기로 확정한다. 실제로 문제가 생기면 그때 넉넉한 상한(예: 300페이지)을 추가한다.

목록 조회 자체(후보 이름만 받는 것)는 각 페이지가 빠르므로(9페이지에 약 2초, §6 실측) 이 단계는 기존처럼 한 번에 끝낸다. 느려지는 지점은 항상 그다음의 본문 상세 검증 단계였다.

### 5.2 우선순위 분류

순수 함수 `classify_candidates(candidates, priority_keywords) -> tuple[priority, rest]`를 `service.py` 또는 새 모듈에 추가한다. 판단 기준은 후보의 법령명·행정규칙명·자치법규명에 우선순위 키워드 중 하나라도 부분 포함되는지 여부다(이 분류는 결과 채택 여부와 무관한 "검증 순서"만 결정하므로, 여기서는 부분 포함으로 충분하다 — 최종 결과 채택은 여전히 `detail.py`의 정확 일치 검증을 통과해야 한다).

우선순위 키워드가 비어 있으면(§9 확정 전 또는 사용자가 끈 경우) 전체를 "우선순위"로 취급해 지금과 동일하게 한 번에 검증한다 — 즉 이 기능은 켜져 있지 않아도 지금 동작으로 정확히 되돌아간다.

### 5.3 1차 검증과 렌더링

우선순위 후보만 기존 `_verify_body_results()` 경로로 검증하고, 기존과 동일한 화면 구조(사이드바, 그룹, 카드)로 즉시 렌더링한다. 이 단계의 체감 속도는 지금과 같거나(우선순위 후보 수가 적으면) 더 빠르다.

### 5.4 2차 검증 — 점진적 진행

나머지 후보는 `st.fragment(run_every="2s")`로 감싼 작은 상태 조각 안에서, 매 재실행마다 다음 청크(예: 20~30건)를 검증하고 세션 상태의 결과 목록에 append한다. 이 fragment는:

- 검증 대기열, 완료된 결과, 진행 카운트를 `st.session_state`에 보관한다(다른 스레드를 쓰지 않으므로 세션 상태 접근이 항상 메인 스크립트 컨텍스트 안에서 안전하다).
- 화면에는 `나머지 확인 중… (350 / 706)` 같은 한 줄만 갱신한다. 이 fragment 밖의 나머지 화면(검색창, 이미 뜬 카드)은 다시 그려지지 않는다.
- 새로 확인된 결과가 생기면, 해당 결과가 속한 기존 그룹(법률/대통령령/…)에 그대로 append한다 — 별도의 "우선순위 결과" 섹션을 새로 만들지 않는다.
- 모두 끝나면 `총 806건 확인 완료 (추가 2건 발견)`처럼 한 번 더 상태를 바꾸고 자동 재실행을 멈춘다.

**2026-09-09 결정 기록 (최종 브랜치 리뷰):** 청크 검증 중 새로 확정된 결과가 있으면(즉 `confirmed`가 비어있지 않으면) fragment 스코프가 아닌 전체 스코프로 `st.rerun()`을 호출해 화면에 즉시 반영한다. 이는 이번 브랜치의 실제 구현이며, "fragment만 다시 그린다"는 위 문장과 "버튼 없이 검색 결과 목록에 바로 추가한다"는 요구사항이 Streamlit 구조상(부모 스코프에 그려진 내용은 fragment가 갱신할 수 없음) 동시에 완전히 만족될 수 없다는 점이 최종 리뷰에서 확인됐다. 사용자가 반복적으로 요구한 "버튼 없이 자동으로 결과 목록에 바로 추가"를 "fragment만 다시 그린다"보다 우선한다 — 확정 건이 없는 빈 틱에서는 기존처럼 fragment만 다시 그려지므로, 화면 전체가 매 2초 재실행되는 것은 아니다.

## 6. 성능 실측 근거

"통합심의" 법률 검색(`totalCnt=806`) 기준:

- 목록 조회(페이지 9개, 페이지당 `display=100`)를 순차로 다 받아도 약 2.17초.
- 상세 본문 검증(자료원당 동시성 4)이 실제 체감 지연의 대부분을 차지한다 — 이 단계를 우선순위/나머지로 나누는 것이 이번 설계의 핵심이다.

## 7. 캐시와의 관계

- 목록 캐시는 지금처럼 검색어·자료원·페이지 단위로 저장하되, 이제 여러 페이지가 저장 대상이 된다. TTL은 기존과 동일(24시간).
- 상세 문서 캐시(본문 검증에 쓰는 캐시)도 기존 그대로 재사용 — 우선순위든 나머지든 같은 캐시 저장소를 쓴다.
- 새로고침(`refresh=True`) 시에는 지금처럼 캐시를 건너뛰고 전체를 다시 받는다.

## 8. 오류와 경계 상황

- 페이지 추가 조회 중 일부 페이지가 실패하면, 성공한 페이지의 후보만으로 계속 진행하고 나머지는 §9와 무관하게 그 자료원의 기존 `SourceState.ERROR`/부분 실패 처리 방식을 따른다(새 예외 유형을 만들지 않는다).
- 사용자가 검증 완료 전에 새 검색을 실행하면, 진행 중이던 2차 검증은 폐기하고 새 검색으로 대체한다(현재 `_clear_response`가 이미 이 역할을 한다).
- 우선순위 키워드가 없거나 전부 매칭 안 되면(모든 후보가 "나머지"), 1차 렌더링은 빈 결과로 뜨고 2차 진행이 사실상 전체 검증이 된다 — 이 경우도 예외 없이 정상 동작해야 한다(즉 "우선순위 후보가 0건"은 에러가 아니다).

## 9. 우선순위 키워드 (확정)

사용자의 실무 도메인(건설사업관리·정비사업)을 반영해 확정한 41개 키워드(아래 목록, `src/lawsearch/prioritization.py`의 `PRIORITY_KEYWORDS`와 정확히 일치). `classify_candidates()`가 법령명·행정규칙명·자치법규명에 이 중 하나라도 부분 포함되면 "우선순위"로 분류한다. 코드 안에 상수로 넣는다(설정 화면 노출은 이번 범위 밖, §4 제외 참고). 나중에 추가·삭제해도 순서만 바뀔 뿐 결과 채택 여부(정확 일치 검증)에는 영향이 없다.

- 정비사업 핵심: 도시, 주택, 주거, 정비, 재건축, 재개발, 도심
- 인허가·계획: 국토, 개발, 건축, 택지, 혁신도시, 공업지역, 부동산
- 기반시설·설비: 도로, 하천, 수도, 하수도, 공원, 녹지, 교통, 주차장, 설비, 전력, 에너지
- 안전·재난: 소방, 화재, 재난, 위험물, 안전관리, 승강기, 다중이용업소
- 환경·자연: 환경, 산지, 산림, 농지
- 행정·재무: 조세, 감정평가, 건설산업
- 기타: 문화재, 장애인

청크 크기(2차 검증에서 한 번에 몇 건씩 처리할지)와 fragment 주기(2초 vs 다른 값)는 구현 중 실측하며 조정한다.

## 10. 테스트 전략

- `classify_candidates()`는 순수 함수이므로 키워드 포함/불포함/키워드 없음(전체 우선순위 취급) 케이스를 API 접근 없이 단위 테스트한다.
- 페이지 전체 조회 로직은 `httpx.MockTransport`로 `totalCnt`가 큰 응답을 흉내내 여러 페이지가 실제로 호출되는지 검증한다(기존 `test_api.py`/`test_service.py` 패턴 재사용).
- 기존 "방화구획" 회귀 테스트(오탐 제외)는 그대로 통과해야 한다 — 이번 변경은 후보를 "더 많이 보되 여전히 정확 일치만 채택"하는 것이지, 검증 기준을 느슨하게 하는 게 아니다.
- fragment 기반 점진적 렌더링은 Streamlit 통합 테스트(`streamlit_stub.py`의 `FakeStreamlit`)로, "우선순위만 있을 때"와 "우선순위+나머지 둘 다 있을 때" 최종 화면 상태를 검증한다.

## 11. 구현 순서

1. 전체 페이지 조회(§5.1) — 기존 회귀 테스트가 계속 통과하는지 먼저 확인.
2. `classify_candidates()` 순수 함수 + 단위 테스트.
3. 1차(우선순위) 검증·렌더링 경로 — 우선순위 키워드가 비었을 때 지금과 동일하게 동작하는지 회귀 테스트로 고정.
4. `st.fragment` 기반 2차 진행 + 상태 표시.
5. 새 결과 자동 append 로직.
6. 실제 "통합심의" 검색으로 로컬 수동 검증(도시정비법이 이제 뜨는지).
